# Firehouse Deluxe

## Что делаем

- Делаем шуточный ремейк **Fisher-Price: Firehouse Rescue** для NES.
- Игра полностью 2D. Для текущего прототипа пожарной машины используется вид сверху и автомобильное управление в духе GTA 1: газ, торможение, задний ход и плавные повороты на любой угол.
- Визуальный стиль — **пиксельная графика** с сохранением шуточного характера ремейка.
- Ориентир для графики — оригинальная игра. Текущие уровни собираем из тайлов; готовая картинка оригинальной карты не является основой тайлового уровня.
- Пиксельные ассеты сохранять чёткими: без размытия и сглаживания при импорте, с фильтрацией Point. Сохранять исходники в оригинальном разрешении.
- Временные условные спрайты допустимы для прототипов, но не определяют финальный стиль.
- Юмор и намеренная кривизна допустимы в художественной подаче. Управление, поведение игры и качество кода должны быть понятными и предсказуемыми.

## Техническая основа

- Unity **6.3 LTS**, текущая версия проекта — `6000.3.17f1`.
- Universal 2D / URP, C#, установленный Unity Input System.
- Основные игровые файлы: `Assets/FirehouseDeluxe/`.
- Рабочая сцена — `Assets/Scenes/RoadPlayground.unity`, открываемая меню `Firehouse Deluxe → Tile Editor`. Старые тестовые сцены удалены; не восстанавливать их без отдельной задачи.
- Уровень строится настоящими тайлами 8×8 пикселей, без привязки к временной картинке карты. При 4 Pixels Per Unit размер клетки Grid — 2×2 единицы Unity, без сдвига в пиксель.
- В Tile Palette `Road Palette`: чёрный `Road` — проезжая дорога без коллайдера, зелёный `Ground` — непроезжая земля с коллайдером. Дорогу убирать заменой на `Ground`; пустая клетка после ластика не создаёт препятствие.
- Для автомобиля: движение в плоскости XY, нос спрайта направлен вдоль локальной +Y, поворот вокруг Z, физика через `Rigidbody2D`.
- Не добавлять сторонние пакеты, если задачу разумно решить имеющимися средствами. Существенные зависимости согласовывать с пользователем.

## Код: понятность и DRY

- Писать простой, читаемый код с понятными именами и небольшой областью ответственности у каждого компонента.
- Соблюдать DRY: общая логика должна иметь одно место определения. При этом не создавать абстракции ради устранения случайно похожих строк.
- Использовать минимальную архитектуру, достаточную для текущей задачи. Не добавлять системы и универсальные фреймворки на вырост.
- Разделять ввод, игровую логику и отображение там, где это упрощает изменение и понимание кода.
- Параметры, которые нужно подбирать на глаз и по ощущениям, открывать в Inspector через сериализуемые поля. Не дублировать настройки в нескольких местах.
- Физику обновлять в `FixedUpdate`, считывание ввода — в соответствии с настройками Input System, следование камеры — в `LateUpdate`.
- Комментарии должны объяснять причины и неочевидные решения, а не пересказывать код.
- Не проводить несвязанный рефакторинг и не перезаписывать пользовательские сцены, ассеты или настройки без необходимости для задачи. Сохранять существующие `.meta` и ссылки на ассеты.

## Проверка и работа с пользователем

- **Ручное тестирование игры в Unity выполняет пользователь.** Он проверяет геймплей, визуал и ощущения от управления.
- После изменения давать короткую инструкцию: какую сцену открыть, что нажать и какое поведение проверить. Указывать, где находятся доступные настройки в Inspector.
- Не запускать Unity ради тестирования, не открывать второй редактор и не создавать отдельные копии проекта для проверок по собственной инициативе. Такие проверки выполнять только по явной просьбе пользователя.
- По умолчанию не добавлять и не запускать автоматические игровые тесты; необходимость таких тестов обсуждать отдельно. Наличие тестов в проекте само по себе не означает просьбу их запускать.
- Доступные проверки исходников и ошибок компиляции можно выполнять без запуска отдельной Unity. Не выдавать проверку кода за проверку игры в Play Mode.
- Чётко сообщать, что реализовано, что фактически проверено и что предстоит проверить пользователю.
- Обсуждать проект с пользователем на русском языке.
